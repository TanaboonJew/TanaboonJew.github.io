Foreman

A workflow orchestrator for coding agents: configurable role pipelines on top of OpenCode, with persistent state, approval gates, and resumable runs.

Active 2025 RustTauriOpenCodeAgent orchestrationCLI

The idea

Handing a coding agent one giant task and walking away produces exactly what you’d expect: one giant result, and no way to tell where it went wrong. Foreman is the opposite of that. You give it a goal, it plans, and every stage of the pipeline is a checkpoint you can inspect, approve, reject, or rerun before anything touches your repository.

The division of labor is deliberate:

Foreman decides who works, in what order, under what constraints, and when a human must intervene. OpenCode decides how an individual coding agent actually performs its work.

Foreman is not an LLM client and not another coding agent. It is the layer above the coding agent. Provider credentials, tool execution, permissions, MCP, sessions — that all stays in OpenCode. Providers like OpenRouter and Ollama sit behind OpenCode too, so Foreman can put a cloud reasoning model on the planner and a local model on the implementer without ever seeing an API key.

Foreman ──▶ OpenCode ──▶ OpenRouter ──▶ cloud model
                └──────▶ Ollama ──────▶ local model

Roles are markdown files with YAML frontmatter — name, description, optional provider/model plus variant, and a named permission policy. Pipelines are YAML: stage ids, role assignments, approval gates, and explicit on_revise / on_fail transitions. Nothing about the flow is implicit or hardcoded.

Engineering notes

  • One OpenCode session per stage. A run gets separate sessions for gather, plan, implement, and test — parallel workers get their own sessions too. Session IDs are persisted in the run manifest, so transcripts stay isolated by role and every stage remains independently retryable and auditable.
  • Real state machine, real persistence. Stages move through pending → running → awaiting_approval → succeeded/failed/rejected/cancelled, and every transition lands in run.json, an append-only events.ndjson, and human-readable run.md. foreman resume <id> genuinely reconstructs state from disk; foreman rerun <id> --stage plan resets exactly the downstream work.
  • Approvals are stored objects, not chat replies: decision (approve / reject / revise), timestamp with timezone offset, and an optional note. The GUI surfaces them as hard gates — the pipeline physically stops without one.
  • Policies are separated from models. Four built-in permission profiles (readonly, workspace-write, test-fix, unrestricted) map onto OpenCode’s allow/ask/deny capability rules, including bash command patterns. Every default denies git commit and git push. The default pipeline ends at a validated working tree, never at an autonomous merge.
  • Dynamic model discovery. Foreman ships no model catalog. It asks the OpenCode server what providers and models exist, validates each role’s assignment against that live catalog before running, and fails with a clean “model unavailable, did you mean…” error instead of a mystery crash. Managed mode spawns and supervises its own loopback-only OpenCode server with per-launch credentials; attach mode connects to one you already run.
  • foreman doctor. One command checks executable, server health, provider connectivity, workspace writability, and run-directory access — exit code friendly for CI.
  • The fake worker makes testing honest. An offline deterministic worker replays scripted outputs, so the whole orchestration layer — gates, transitions, artifact writing — is tested without touching a model or network. The HTTP client is tested against a scripted mock server; live OpenCode integration tests are gated separately, so ordinary test runs never touch a real server or cost tokens.
  • Run folders are the audit trail. Manifest, per-stage transcripts, diffs, approvals, and the event log are plain files. You can inspect a complete run with cat and grep, no app required.
  • Desktop GUI over the same state. foreman with no arguments opens a Tauri app that reads and writes the same run folders as the CLI — launch runs, watch stages move, decide at gates, inspect diffs per stage. No second source of truth, no web service to deploy.
